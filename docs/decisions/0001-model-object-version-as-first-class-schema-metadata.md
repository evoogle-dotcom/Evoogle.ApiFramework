# Model Object Version as First-Class Schema Metadata

## Status

Accepted on 2026-09-09. Schema and value foundation implemented on 2026-09-10.

## Context and Problem Statement

`ApiObjectType` describes API-visible object structure, keys, and relationships. The runtime can
materialize an `ApiKey` from an object according to an `ApiKeyType`, but it does not yet have an
equivalent schema concept for the version of an object's state.

The operation architecture requires versions to support optimistic concurrency consistently across
clients, services, providers, and heterogeneous repositories. A version may be stored in a CLR
member, supplied as repository metadata, represented as an HTTP entity tag, or generated by another
service. It must not be confused with an object's stable identity or with `ApiSchema.ApiVersion`.

This record defines the required semantics and feature boundary. The implemented public metadata
type is `ApiVersionType`; its materialized runtime value is `ApiVersion`.

## Decision Drivers

- Make optimistic concurrency a provider-neutral API semantic.
- Preserve the distinction between stable object identity and changing object state.
- Support POCO-backed and repository-supplied versions.
- Allow different command targets for one object type to apply different concurrency policies.
- Keep version comparison and mutation atomic at the repository boundary.
- Make versions available to client state management without requiring them in every projection.
- Reuse the schema compilation, freezing, materialization, JSON, and extension conventions already
  established by the framework.

## Considered Options

1. Include the version in `ApiObjectIdentity`.
2. Treat a designated ordinary property as a version by convention only.
3. Keep versions entirely inside repository implementations.
4. Add first-class object-version metadata and a distinct materialized version value.

## Decision Outcome

Choose option 4: add first-class version metadata to `ApiObjectType` and materialize a distinct,
immutable object-version value from an object or repository result.

Conceptually:

```text
ApiObjectType
├── ApiKeyTypes
├── ApiProperties
├── ApiRelationships
└── optional ApiVersionType

Object occurrence
├── ApiObjectIdentity
├── ApiVersion
└── object state
```

`ApiObjectIdentity` continues to contain the applicable `ApiNamedKeyType` and materialized
`ApiKey`. Version is not part of identity.

## Required Semantics

### One optional version definition per object type

An `ApiObjectType` may declare one version definition. An object type without one remains valid and
does not participate in version-based concurrency unless another future concurrency mechanism is
explicitly introduced.

The version definition is owned by the object type, participates in schema compilation and
freezing, and is navigable as structural schema metadata.

The singular `ApiObjectType.ApiVersionType` property makes multiple in-memory definitions
structurally impossible. Repeated fluent configuration replaces the prior definition. Duplicate
`ApiVersionType` members in one object-type JSON object are rejected as malformed JSON rather than
represented as a plural schema model.

### Version and identity remain separate

Identity answers which logical object is referenced. Version answers which observed state of that
object is referenced.

```text
Customer identity 42, version 6
Customer identity 42, version 7
```

These are two states of the same object, not two object identities. Identity maps remain keyed by
canonical object identity and retain the currently observed version as entry state.

### Version values are immutable and opaque

A materialized object version is immutable. Its required semantic operation is equality. Ordering,
arithmetic, and user mutation are not implied.

The first version supports a single non-null scalar value. The scalar may represent common version
forms such as an integer, GUID, timestamp, string entity tag, binary row version, or custom scalar.
Composite version values are deferred.

The exact CLR representation participates in equality: an `int` version does not equal a
numerically identical `long` version. Strings use ordinal equality. Recognized binary forms are
defensively copied and use structural equality.

Custom reference-type scalar versions are supported as an explicit integration opt-in. The
`ApiVersion` retains the supplied reference because an arbitrary third-party type cannot be deeply
copied safely or generically. The supplied object must therefore remain immutable while used as a
version and must provide stable equality and hash-code behavior. Mutating it after materialization
can invalidate equality or dictionary behavior; the framework cannot enforce this contract.

### Property-backed and repository-backed versions

The version definition supports both of these sources:

- A schema property backed by a CLR property or field.
- Opaque repository metadata with no required CLR member.

The standard runtime materializes property-backed versions through compiled schema accessors.
Repositories return repository-backed versions explicitly.

The implemented shape is:

```csharp
public sealed class ApiVersionType : ApiSchemaElement
{
    public ApiVersionType(string clrMemberName);
    public ApiVersionType(Type clrType);

    public Type ClrType { get; }
    public string? ClrMemberName { get; }
    public ApiScalarType ApiScalarType { get; }
    public ApiProperty? ApiProperty { get; }
    public bool IsPropertyBacked { get; }
    public bool IsRepositoryBacked { get; }

    public ApiVersion MaterializeVersion(object clrObject);
    public ApiVersion MaterializeVersionFromValue(object? value);
}
```

Property-backed definitions supply only `ClrMemberName`. The referenced member must already be an
`ApiProperty`; version configuration does not silently add it. It must be required and scalar, and
the CLR member must use the same exact CLR type as the resolved `ApiScalarType`.
Repository-backed definitions instead supply only `ClrType`, which resolves the registered
`ApiScalarType`. After compilation, `ApiScalarType` is the authoritative scalar metadata for both
sources and `ClrType` is derived from it.

JSON likewise contains exactly one source property: `ClrMemberName` for property-backed metadata
or `ClrType` for repository-backed metadata. Supplying both or neither is malformed.

### Versions are normally generated by the service

Create produces an initial version. A successful update produces a new version. A client does not
change a version through an ordinary create or update property assignment unless a future explicit
policy allows that behavior.

Version input used for concurrency is represented as an expected version, not as a patch to the
version property.

### Command-target contracts define concurrency policy

Version semantics belong to `ApiObjectType`; mutation requirements belong to each
`ApiCommandTarget` contract.

A create, update, or delete contract can declare version behavior independently, including whether
an expected version is required, optional, or unsupported. Multiple command targets over the same
object type may expose different policies.

### Repository retrieval preserves version

Repository query and identity retrieval preserve the version alongside each returned POCO. The
standard operation execution scope stores the observed version with the identity-mapped object.

The version remains available as execution metadata even when the query projection does not expose
the version property as result data.

### Patch and delete enforce versions atomically

An update or delete carrying an expected version must enforce that version inside the repository's
atomic mutation boundary. Loading an object, checking its version in the standard runtime, and then
performing an unconditional mutation is not sufficient because state may change between the check
and write.

Conceptually:

```text
Patch Customer 42
├── ExpectedVersion: 6
└── Changes
    └── Name = "Alice"

Repository atomic condition:
    Identity = 42 AND Version = 6
```

The repository distinguishes at least target absence, version conflict, successful application,
and infrastructure failure. The standard command executor maps those facts into canonical command
outcomes.

### Successful commands report resulting versions

A successful create or update reports the resulting version as standard command-result metadata,
independently of any optional projected result data. Update results may also report the previous
version when available. Delete results retain the expected/deleted version information needed for
diagnostics but do not create a post-delete version.

### Providers preserve version semantics

Providers map canonical versions to protocol representations without defining their meaning.
Examples include HTTP entity tags, GraphQL fields or mutation inputs, and gRPC message fields.

Provider capability analysis rejects a version-dependent command when the provider cannot preserve
the required concurrency contract.

## Schema Integration Requirements

Implementation must coordinate the version feature across applicable surfaces:

- `ApiObjectType` ownership and lookup behavior.
- Schema builders and configuration state.
- Schema compilation diagnostics and lifecycle.
- Frozen publication and extension snapshots.
- CLR property or field binding.
- Runtime version materialization.
- Schema JSON round-tripping.
- Object-type conventions where explicitly enabled.
- Query and repository retrieval records.
- Command-target concurrency policies.
- Create, patch, and delete repository contracts.
- Command results and client materialization/state reconciliation.
- Tests following repository xUnit conventions.

### Declarative version configuration

The POCO-safe annotations package provides one dual-purpose `ApiVersionAttribute`. Applying
`[ApiVersion]` to a property or field declares a property-backed version; member annotations must
not specify `ClrType`. Applying
`[ApiVersion(ClrType = typeof(TVersion))]` to an object type declares a repository-backed version.

The annotation designates version metadata only. It does not register the version scalar, add the
member as an API property, or make that property required. The same compilation requirements apply
to annotated and fluent definitions.

Version annotations participate at data-annotation precedence. Explicit fluent configuration wins
over annotations, annotations win over conventions, and later annotation readers replace earlier
readers. Multiple valid declarations from one reader are rejected as a version annotation
conflict.

## Validation Requirements

Schema compilation must diagnose at least:

- Duplicate version metadata in object-type JSON (the singular CLR model cannot contain more than
  one definition).
- Version-type JSON that contains both or neither source property.
- An unresolved or incompatible CLR member binding.
- A non-scalar or nullable first-version representation.
- A version definition whose scalar type is unresolved.
- A command-target contract requiring versions from an unversioned object type.
- Invalid generated-versus-client-supplied version policy combinations.
- Mutable or otherwise invalid frozen extension snapshots.

Runtime preparation or execution must diagnose at least:

- Missing required expected versions.
- Expected versions with incompatible scalar data.
- Repository results missing required versions.
- Repository-returned versions incompatible with the object type's definition.
- Atomic version mismatches as conflicts rather than generic failures.

## Consequences

### Positive

- Optimistic concurrency has one canonical meaning across protocols and repositories.
- Identity maps continue to represent logical objects rather than individual revisions.
- POCO-backed, remote, document, and HTTP-style version tokens fit the same model.
- Command results can support later client state tracking without requiring visible version fields.
- Version-aware providers and repositories can negotiate support explicitly.

### Negative

- Schema compilation, JSON, builders, repositories, commands, results, and tests all gain another
  coordinated metadata concept.
- Repository mutation contracts become more capable than unconditional CRUD methods.
- Repository-returned metadata must remain aligned with POCO state.
- The term `Version` requires careful naming to avoid confusion with `ApiSchema.ApiVersion`.

### Neutral and Follow-up Work

- Repository retrieval records, command-target concurrency policies, atomic mutation contracts,
  provider mappings, and client state reconciliation remain part of the operation-runtime work.
- Composite concurrency tokens are deferred.
- Temporal history, event sourcing, and retrieval of historical versions are not part of this
  decision.
- Cross-object transaction versions are not part of this decision.
- Persistent client state tracking is deferred to the state-pipeline architecture.

## Confirmation

The schema and value foundation is confirmed when focused tests demonstrate:

- Successful compilation and freezing of property-backed and repository-backed version metadata.
- Version materialization from supported CLR and repository values.
- Schema JSON round-tripping version metadata.
- UTF-8 BOM, CRLF, build, test, and scoped diff verification required by the repository.

The deferred operation-runtime work is confirmed separately when tests demonstrate identity
separation, returned versions, command-target policies, and atomic create, patch, and delete
behavior.
